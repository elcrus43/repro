# Технический аудит REA CRM

Дата: 2026-10-23. База: HEAD 286ecd1 и существующие локальные изменения.
Область: серверные API, авторизация, публичные страницы, синхронизация, Python messaging, зависимости и команды проверки. Это аудит исходного кода; конфигурация и данные production не проверялись.

## Критичные проблемы

### 1. P0: SQL API позволяет читать и менять чужие записи и повышать роль

Места: api/neon-query.js:95-120, 153-170; neon-schema.sql:5-6.

JWT проверяется, но его sub и role не ограничивают выполняемый SQL. userId можно не присылать. В схеме RLS удалён. Разрешены profiles и user_sessions, а ограничения записей формируются клиентом. Запросы SELECT * FROM profiles и UPDATE profiles SET role = $1 WHERE id = $2 проходят обработчик для обычного пользователя.

Подтверждение: вызов фактического обработчика с подменённой БД и проверкой JWT вернул 200 и дошёл до sql.query для обоих запросов. Реальная БД не использовалась.

Исправление: заменить произвольный SQL именованными серверными операциями; проверять владельца и административные права на сервере, ограничить изменяемые поля и права DB-роли.

### 2. P0: публичный JOIN допускает выбор password_hash

Места: api/neon-query.js:34-35; neon-schema.sql:32.

Публичная регулярка допускает произвольное содержимое json_build_object. Анонимный запрос SELECT p.*, json_build_object('password_hash', prof.password_hash) as profiles FROM properties p LEFT JOIN profiles prof ON p.realtor_id = prof.id WHERE p.id = $1 проходит проверку. При известном ID объекта можно запросить хэш пароля связанного риелтора. Проверки активной публичной ссылки здесь также нет.

Подтверждение: обработчик с подменённой БД вернул 200 без заголовка Authorization.

Исправление: публичная серверная операция по slug, проверка активности ссылки, фиксированная проекция разрешённых полей. Удалить клиентский SQL из публичного контракта.

## Высокий приоритет

### 3. P1: штатная синхронизация отдаёт все поля всех профилей

Место: src/context/neonSync.js:151-162.

Даже ветка обычного риелтора агрегирует все profiles без списка колонок. По схеме в них есть password_hash и passport_details. Это выдача чувствительных данных при штатной загрузке, помимо возможности произвольного SQL из пункта 1.

Исправление: отдельная безопасная проекция публичных профилей; реквизиты и авторизационные данные получать только специализированными серверными операциями.

### 4. P1: модерация аккаунтов обходится при регистрации и refresh

Места: api/neon-auth.js:173-193, 221-244; api/neon-query.js:104-120.

Регистрация создаёт pending-профиль, но сразу возвращает полноценный JWT и сессию. Query API не проверяет статус. Refresh также выпускает токен без проверки pending/rejected. Проверка статуса только в login не обеспечивает модерацию доступа.

Исправление: не выдавать рабочую сессию pending-пользователю; проверять актуальный статус на защищённых операциях и refresh.

### 5. P1: logout и блокировка не отзывают доступ существующего JWT

Места: api/neon-auth.js:250-255; api/neon-query.js:104-120; api/google-calendar-token.js:30-36.

Logout удаляет user_sessions, но защищённые API проверяют только подпись и срок JWT. Скопированный токен сохраняет доступ до 7 дней. Смена пароля также не отзывает сессии.

Исправление: проверять активную сессию и статус профиля, отзывать сессии при блокировке и смене пароля; использовать уникальный идентификатор сессии.

### 6. P1: Python messaging не проверяет пользователя и владельца

Места: backend/app/api/messaging.py:22-25, 59-66, 85-92.

Список шаблонов возвращается целиком, удаление выполняется по произвольному ID, а user_id напоминаний задаёт вызывающая сторона. Depends(get_db) даёт соединение, но не авторизацию. При доступности FastAPI извне эти операции доступны анонимно.

Исправление: зависимость аутентификации, user_id из проверенной сессии, фильтры владения во всех запросах.

### 7. P1: AI proxy открыт для анонимного расходования квоты

Место: api/ai-proxy.js:28-112.

Генерация, распознавание документов и обращения к DB-аналогам выполняются без JWT и лимита пользователя. CORS не является контролем доступа. Анонимные вызовы могут расходовать оплачиваемые ключи провайдеров.

Исправление: серверная проверка сессии, квоты, ограничение размера и количества входных данных, общий бюджет времени для fallback-цепочки.

## Функциональные ошибки

### 8. P1: фильтр SQL ломает обновления updated_at

Место: api/neon-query.js:154.

Регулярка UPDATE не требует границы слова после ключевого слова. Она распознаёт updated_at как UPDATE + d_at и отклоняет запрос с Access denied to table: d_at. Это затрагивает публичный UPDATE matches (src/pages/Clients/PublicClientPage.jsx:70) и обычные изменения с updated_at.

Подтверждение: оба запроса UPDATE matches SET status = $1, updated_at = $2 WHERE id = $3 и UPDATE clients SET updated_at = $1 WHERE id = $2 RETURNING * получили 403 на подменённой БД. Первый вообще пропускается публичной проверкой, но затем отклоняется фильтром таблиц. Поэтому анонимная запись статуса в текущем дереве не подтверждена; отсутствие проверки токена подборки остаётся дефектом контракта.

Исправление: серверные операции вместо regex-разбора SQL; исправление границы слова требует одновременно закрыть публичное изменение без проверки токена.

### 9. P1: гостевой чат требует JWT CRM

Места: src/pages/Messaging/PublicChatPage.jsx:37-54; api/neon-query.js:95-101.

Гостевая страница выполняет SELECT deals, который не входит в публичные запросы. Новый посетитель без сессии получает 401. Дополнительно t_sec-токен вычисляется из ID сделки и не является серверным секретом.

Подтверждение: запрос страницы без Authorization получил 401 в локальном обработчике.

Исправление: отдельный гостевой API с криптографически случайным отзываемым токеном, проверкой сделки и стороны чата на сервере.

### 10. P1: создание шаблона сообщения использует неверный объект

Место: backend/app/api/messaging.py:39-52.

Pydantic-данные приходят в req, но код обращается к request.body, request.name, request.category и request.channels. request.body является методом Starlette Request, а не текстом шаблона. extract_variables получит метод вместо строки и завершится TypeError ещё до INSERT.

Исправление: использовать req.body, req.name, req.category, req.channels и авторизованный user_id.

### 11. P2: восстановление пароля сообщает успех без действия

Место: src/lib/neonAuth.js:200-205.

resetPasswordForEmail ничего не отправляет и возвращает error: null. Пользователь получает ложное подтверждение восстановления.

Исправление: реализовать серверный flow восстановления или явно показывать доступный способ обращения к администратору.

## Зависимости и проверки

- npm audit --omit=dev --json: 2 уязвимых пакета, dompurify (critical, транзитивный, fixAvailable=true) и xlsx (high, прямой, fixAvailable=false в npm-отчёте). Требуется обновление/замена и проверка реальных путей обработки файлов.

Полные команды запущены в фоне с логами reacrm-audit-{test,lint,build}.log в C:/Users/l4gn/AppData/Local/Temp/opencode.
- package.json не содержит test:e2e, хотя AGENTS.md приводит такую команду. Документация также описывает Supabase как основной backend при фактическом Neon по умолчанию.

- Итог фоновой production-сборки: успешно, 2139 модулей, 8 минут 59 секунд.
- В существующих локальных изменениях git сообщает о CRLF, несмотря на правило LF. Файлы пользователя не нормализовались в рамках аудита.
